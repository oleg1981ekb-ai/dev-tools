# AGENTS.md

Инструкции и контекст для AI-агентов и ассистентов, работающих с этим репозиторием.
(Стандарт: [agents.md](https://agents.md).)

## О проекте

`dev-tools` — личный monorepo-инкубатор утилит одного разработчика
(`oleg1981ekb-ai`). Стратегия — **«инкубатор → продукт»**: проект живёт здесь,
пока не созреет для отдельного репозитория. Критерии и порядок выделения —
в разделе «Стратегия развития» [README.md](README.md).

Актуальный план работ, состояние задач и **имена рабочих веток** — в
[TODO.md](TODO.md). Обновляй `TODO.md` при закрытии или появлении задач.

## Правила (обязательны)

1. **Секреты и данные клиентов — никогда в git.** `.env`, `.env.*` (кроме
   `.env.example`), клиентские PDF/Excel/CSV и извлечённый текст исключаются
   через `.gitignore` (корневой и проектный). Не ослабляй эти правила.
   Дополнительно: не выводи ключи в логи и промпты LLM; клиентские документы
   не отправляй во внешние API без согласия; при подозрении на утечку —
   ротировать ключ.
2. **Один коммит — одна тема.** Не смешивать уборку, рефакторинг и
   функциональные правки.
3. **Ветки:** `main` — стабильное состояние; фичи — в `feature/*` (и `fix/`,
   `docs/`, `chore/`, `refactor/`, `test/`), затем PR в `main`. Актуальные
   рабочие ветки указываются в `TODO.md`, а не здесь. Обязательное создание
   ветки перед правками — см. правило 10.
4. **Не коммитить мусор и артефакты:** `.DS_Store`, `__pycache__`, `.venv`,
   `.~lock.*`, `temp.zip`, `dist/`, `build/`, `*.spec`, `.pytest_cache/`,
   `.ruff_cache/`, сгенерированные `*.xlsx`/`*.csv`/`*.pdf`.
5. **CI проекта** срабатывает только при изменении его папки (фильтр `paths`).
   Новые CI добавляй с такими же фильтрами (например,
   `paths: ['PDF_Excel_compare/**']`).
6. **Архитектурные решения — в ADR.** Любое значимое решение
   (выбор метода/формата/стратегии, отказ от альтернативы) фиксируй файлом
   `docs/adr/NNNN-*.md` (следующий номер = max+1, сейчас 0004) в формате
   Контекст → Решение → Последствия. Триггеры: «почему так, а не иначе»,
   «что пробовали и отбросили», смена подхода в ветке.
   Принятый ADR не правится задним числом — отмена только новым ADR.
   Индекс и статусы — в `docs/adr/README.md`.
   При закрытии задачи проверь: нужен ли ADR, обновлён ли `TODO.md`.
7. **Ченджлог.** При мерже задачи в `main` добавь запись в `CHANGELOG.md`
   соответствующего продукта (раздел `Unreleased`, категория
   `Added/Changed/Fixed/Removed`, формат Keep a Changelog). Пиши языком
   пользователя («что изменилось»), не языком коммитов; номер PR — в скобках.
   Технические детали — в ADR. Корневой `CHANGELOG.md` — только для изменений
   уровня репо.
8. **Не сливать ветки в `main` без явного согласования.** Слияние (merge,
   squash-merge, rebase на main) любой ветки в `main` производится только
   после прямого подтверждения пользователя. Коммитить в feature-ветки можно,
   но вливать в `main` — только по команде.
9. **Удалить ветку сразу после слияния.** Как только feature-ветка влита в
   `main` (merge / squash-merge / rebase), удалить её локально и на origin:
   `git branch -d feature/<name>` и `git push origin --delete feature/<name>`.
   Не оставлять отработанные ветки в репозитории.
10. **Не начинать редактирование кода без новой ветки.** Любые изменения кода
    начинаются с создания тематической ветки `feature/*`; правки напрямую в
    `main` не допускаются. Сначала `git checkout -b feature/<name>`, затем
    правки, тесты, коммит, PR и слияние в `main` по правилу 8.

## Определение готовности (DoD)

Задача считается закрытой, только если:

- [ ] изменения сделаны в `feature/*` и соответствуют заявленной теме;
- [ ] тесты проходят (см. «Тесты и проверки»);
- [ ] просмотрен `git diff`: нет секретов, клиентских данных и мусора;
- [ ] обновлены README/TODO/CHANGELOG, при необходимости добавлен ADR;
- [ ] CI зелёный, PR смержен только после согласования (правило 8).
- [ ] **Отслеживание прогресса**: для multi-step задач используй `todowrite` —
      создай список, ставь `in_progress` перед началом шага, `completed` после;
      пользователь видит ход работы в боковой панели.
- [ ] **Явное подтверждение на слияние**: после создания PR спросить у пользователя
      согласия на вливание в `main` и дождаться ответа («да» / «нет»).

## Коммиты и PR

- Сообщение коммита: `type(scope): краткое описание` (Conventional Commits).
  Типы: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`. Тело — по-русски.
- Перед коммитом: `git status --short`, `git diff`, `git log --oneline -5`;
  стейджить только файлы своей задачи.
- PR: что и зачем изменено, как проверено (команды тестов), ссылки на
  TODO/ADR. PR не мержится без явного согласования пользователя.
- Не использовать `--no-verify`, не делать force-push и не амендить
  запушенные коммиты.

## Тесты и проверки

- Тесты — `pytest`, лежат в `<проект>/tests/`. Запуск из папки проекта:
  `python -m pytest -q`.
- Новая логика сопровождается тестом; исправление бага — тестом,
  воспроизводящим баг.
- Линтер/форматтер пока не обязательны: главное — читаемость и единый стиль
  проекта. Если добавляешь инструмент — фиксируй его в `requirements.txt`
  и в этом разделе.
- Зависимости — только в `requirements.txt` проекта, с ограничением версий.

## Окружение

- Python 3.11+ (CI использует 3.11).
- Виртуальное окружение — на проект (`bim-estimate-ai/.venv`,
  `gantt-generator/.venv`), не одно на монорепо; глобально пакеты не ставить.
- Зависимости — в `requirements.txt` проекта, версии с ограничением (`>=`, `<`).
- Пути в скриптах — от `Path(__file__)`, а не от текущей директории.

## Безопасность и данные

- Реальные ключи — только в локальном `.env`; в репозитории допустим
  `.env.example` с пустыми значениями.
- Клиентские PDF, Excel, CSV, `raw_extracted_text.txt` — не коммитить и не
  передавать в сторонние сервисы без согласия владельца данных.
- Не логировать содержимое ключей, токенов и персональных данных.
- При утечке секрета — немедленно ротировать ключ и сообщить пользователю.

## Ведение TODO.md

Единый корневой `TODO.md` ведётся для всего монорепо, а не для каждой папки отдельно:

- **Структура:** разделы по проектам с именами веток (`feature/<name>`).
- **Обновление:** при закрытии задачи — снять галочку, перенести в «Закрыто»; при появлении задачи — добавить пункт в соответствующий раздел.
- **Шапка:** обновить дату актуализации при каждом изменении.
- **Ветки:** актуальные имена рабочих веток указываются только в `TODO.md`, не в `AGENTS.md`.
- **Отдельный TODO в папке продукта:** только если продукт выходит из инкубатора в свой репозиторий (стратегия «инкубатор → продукт»).

## Границы задачи для агента

- Не добавлять зависимости и новые инструменты без согласования.
- Не делать попутный рефакторинг, переформатирование и «уборку» вне задачи.
- Не менять файлы других проектов монорепо в рамках одной задачи.
- Разрушительные операции (`reset --hard`, `push --force`, удаление веток или
  файлов) — только по явной команде пользователя.
- При неоднозначном требовании — задать вопрос, а не выбирать молча.
- Не коммитить сгенерированные артефакты (`.xlsx`, `.csv`, `.exe`, `dist/`).

## Новый проект в инкубаторе

Порядок для новой папки (например, `PDF_Excel_compare/`):

1. Ветка `feature/<name>` (правило 10).
2. `README.md`, `requirements.txt`, `tests/`, проектный `.gitignore`.
3. CI с фильтром `paths` на папку проекта.
4. Строка в таблице структуры корневого `README.md` и в `AGENTS.md`.
5. Задача в `TODO.md`; при значимом выборе — ADR.

## Язык и стиль

- Документация, комментарии, сообщения в консоли — по-русски.
- Идентификаторы в коде, типы коммитов и имена веток — по-английски.
- **Описание проделанной работы, отчеты и финальные ответы пользователю — обязательно на русском языке.**
- Скрипты консольные, интерактивный ввод через `input()`, вывод с
  эмодзи-статусами (✅ ❌ 🚀) — принятый стиль UX утилит.
- Пути в `bim-estimate-ai` — относительные от `Path(__file__)`; PDF ищется
  в `data/` либо передаётся аргументом.
